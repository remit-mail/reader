`repointsOnSighting` requires `syncStatus === synced`. Every row the inbound sync path writes is `pending`, and nothing on that path ever promotes it. So the repoint shipped in #1080 does not fire for ordinary synced-in mail, and mail another client files stays listed in the folder reader first saw it in.

## Where

The gate, `packages/mailbox-service/src/message-sync.ts:154-161`:

```ts
return (
	message.status === MessageStatus.active &&
	message.syncStatus === MessageSyncStatus.synced
);
```

The inbound write, `packages/mailbox-service/src/message-sync.ts:1469-1478`, passes no `syncStatus`:

```ts
const { item, created } = await repos.message.upsertWithStatus({
	messageId, mailboxId, uid: msg.uid, sequenceNumber: msg.seq,
	rfc822Size: msg.size ?? 0, internalDate: msg.internalDate.getTime(),
	envelopeId, rootBodyPartId,
});
```

so `packages/drizzle-service/src/repos/message.ts:186` applies the default:

```ts
syncStatus: input.syncStatus ?? ("pending" as const),
```

Across all packages, only three places ever write `synced`: `repos/message.ts:585` (`updateUid`, which is what the repoint *calls* — downstream, not upstream), `imap-worker/src/handlers/empty-trash.ts:109`, and `imap-worker/src/handlers/message-copy.ts:158`. None is the ordinary inbound path.

The codebase already states this, at `packages/mailbox-service/src/placement-settled.ts:13-15`:

> `syncStatus` is not the signal. An ordinary freshly-synced inbound row is `pending` forever (nothing on the inbound path promotes it), so keying off it defers every outbound mutation in the product. `status` is set to `moving` only by an actual move and cleared only once that move settles.

That file and the #1080 gate hold contradictory assumptions about the same field. A third answer is in the TypeSpec, `typespec/lib/models/Message.tsp:211`, which declares the default `synced` and documents it as *"so a freshly-synced message never looks like it has an outstanding move/delete"* — matching neither the repository default nor the gate.

## Reachability

Caller: `MessageSyncService.trySaveMessage`, `message-sync.ts:1469`. Inputs: any row written by an earlier sync, later sighted in another folder.

`upsertWithStatus` returns `created: false`, `repointsOnSighting` returns false because the stored row is `pending`, so `updateUid` is never called and the listing row keeps the old folder. There is no expunge or VANISHED detection in the forward sync path, so nothing else repairs it — only a UIDVALIDITY rebuild does.

The precondition is ordinary: a second client against the same mailboxes.

## Why the tests did not catch it

`packages/mailbox-service/src/message-sync-repoint.test.ts:59` hardcodes the base fixture:

```ts
status: MessageStatus.active,
syncStatus: MessageSyncStatus.synced,
```

That is a state the inbound path never produces. The suite is green against a row production cannot reach. No e2e exercises a second client filing mail.

## Knock-on

This also defeats the half of #859 that closed today. `reconcileJunkOnlyForMessage` (`packages/drizzle-service/src/repair/junk-only-address.ts:45`) withholds off `message.mailbox_id`; without the repoint that pointer still says INBOX, so the sender is never withheld.

## Fix

Two candidates, and the choice needs stating rather than assuming:

1. Drop the `syncStatus` conjunct and gate on `status === active` alone. `placement-settled.ts` already argues that `status` is the signal and `syncStatus` is not.
2. Write `synced` on inbound save, matching the TypeSpec default.

Whichever is chosen, the regression test must build its row through the real insert path rather than a hand-written fixture — a fixture that asserts an unreachable state is what let this through.
