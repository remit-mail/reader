A recurring event whose first occurrence falls past the expansion horizon is indexed as "fully expanded" with zero rows, so it renders in no calendar view and nothing ever retries it.

## Where

`packages/calendar-service/src/expand.ts:261-267`:

```ts
expandedThrough:
	walk.truncated && walk.lastIteratedStart
		? toUtcIso(Date.parse(walk.lastIteratedStart))
		: "",
```

`walkOccurrences` breaks on the first slot past the horizon (`expand.ts:145-153`) and sets `lastIteratedStart` only for a slot it actually collected (`expand.ts:175`). When the first slot the iterator yields is more than `CALENDAR_EXPANSION_HORIZON_DAYS` (730) past DTSTART, the walk breaks with `occurrences = []` and `lastIteratedStart = ""`. So `truncated` is true and `expandedThrough` is written `""` anyway.

`""` is the sentinel for "the index holds the whole series". `packages/drizzle-service/src/repos/calendar-object.ts:168` filters on it:

```ts
ne(calendarObjectTable.expandedThrough, ""),
```

`listIncompleteExpansions` (`packages/calendar-service/src/window.ts:108-111`) therefore never returns the row, the live-expansion path never fires, and the index stays empty. `expand.test.ts:340` asserts that `""` means complete, so the two meanings are already in conflict.

The event still exists in the store and still serves in the `.ics` feed, which writes raw bytes. It is missing only from the reader's own views, with no error and no marker.

## Reachability

`applyScopedDelete` with `scope=This` writes an EXDATE (`packages/calendar-service/src/scope.ts:486-488`) and re-writes through `putCalendarObject` → `expandCalendar`. So: create `DTSTART:20250301T090000Z` with `RRULE:FREQ=YEARLY;INTERVAL=4`, then delete that single occurrence. ical.js then yields `2029-03-01` first, and the horizon ends `2027-03-01`.

Run against ical.js 2.2.1, that walk returns `collected=0, truncated=true, expandedThrough=""`. `FREQ=YEARLY;INTERVAL=2` with the first two instances EXDATEd behaves the same, as does `FREQ=YEARLY;BYMONTH=2;BYMONTHDAY=29;BYDAY=MO`, whose first slot is 2044.

It is also reachable without a local gesture: `buildAcceptedCalendar` (`packages/calendar-service/src/accept.ts:69-84`) stores an organizer's bytes verbatim, so an invitation carrying a long-interval RRULE with an EXDATE on its first instance is accepted and then never shown.

No test covers a truncated walk that collected nothing — `expand.test.ts:304` and `:328` both cover walks where `lastIteratedStart` is set.

## Fix

When the walk truncated, `expandedThrough` must be non-empty regardless of what was collected — the series start is the honest floor. `""` then means "complete", never "empty", and the row stays visible to `listIncompleteExpansions`.
