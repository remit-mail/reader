An import records unresolved folder references against a `filterId`. If the filter is deleted before its folder is discovered, the binder updates a row that no longer exists, `NotFoundError` propagates out of the mailbox-sync handler, and the reference is never cleared — so every subsequent sync fails the same way and the account stops receiving mail.

## Where

An unresolvable folder becomes a pending reference: `packages/config-transfer/src/import.ts:596-604` pushes `{ kind: FilterAction, target: filterId, … }`, and `:711-722` writes the row as `Pending`.

The binder updates it unguarded — `packages/config-transfer/src/binder.ts:116-118`:

```ts
await repositories.filter.update(accountConfigId, ref.target, {
	actionMailboxId: mailboxId,
});
```

`packages/drizzle-service/src/repos/filter.ts:192-194` throws on a missing row:

```ts
if (!row) {
	throw new NotFoundError(`Filter not found: ${filterId}`);
}
```

and `:198-207` `delete` is a hard delete. `packages/backend/src/handlers/filter.ts:339-354` `deleteFilter` removes the filter and touches no `configImport` row, so the reference outlives its target.

The throw lands in the sync path. `packages/imap-worker/src/handlers/sync-mailboxes.ts:223` awaits `bindImportedFolders` *before* the mailbox collection and message fan-out at `:232`, and `syncMailboxes:150-167` only records `syncPhase: error` and rethrows. `binder.ts:94` performs the `configImport.update` that would drop the reference only after the loop, so the throw leaves `unresolvedRefs` intact and the next sync repeats it.

## Reachability

An import into a fresh instance lands accounts with `connectionState: CredentialsMissing` and `isActive: false` (`import.ts:483`). Such an account holds no mailboxes, so *every* filter with a folder action becomes a pending reference — this is the flagship path, and the wizard shows these as "waiting" (`packages/web-client/src/lib/config-import.ts:381-404`).

The user then enters credentials, discovery runs, and the bind fires. Deleting one imported filter in that window is enough to arm it.

The window is unbounded when the destination server no longer has that path, after a rename or a provider change: the reference waits indefinitely. The binder's own comment says the person may "remove the expectation" — and the only route to do that in the UI is deleting the filter, which is exactly what triggers this.

## Not already covered

The fake filter repository in `packages/config-transfer/src/import.test.ts:224-235` does a `findIndex` and assigns `store.filters[at]` with no not-found branch, so it silently succeeds where the real `FilterRepo` throws. There is no `binder.test.ts` and no e2e case for a deleted filter.

## Fix

Two parts, both needed:

1. In `bindRef`, treat `NotFoundError` from `filter.update` as "the expectation is gone" and drop the reference rather than rethrowing.
2. `bindImportedFolders` must not be able to fail a mailbox sync at all. The call at `sync-mailboxes.ts:223` should not be able to abort the fan-out behind it.

Note the repo's error-handling rule: this is not catch-and-continue hedging of a downstream call. A deleted filter is a designed, expected outcome of the bind — the correct shape is a result the binder returns, not a throw it swallows.
