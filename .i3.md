`readWindow` documents that both ends of a calendar window must carry a zone offset, and the API promises a 400 when they do not. Neither is enforced, so an offset-less window is silently read in the server process's local zone.

## Where

`packages/backend/src/handlers/calendar-event.ts:74-98`. The doc comment states the rule:

> Both ends must carry an offset, because a window with no offset names no span of time — and a client whose `from` was read an hour out gets an apparently empty morning rather than an error.

The code only calls `Date.parse` (`calendar-event.ts:91-92`) and refuses on `NaN`. Both of these parse successfully:

- `Date.parse("2026-01-01T00:00:00")` — read in the server process's local zone
- `Date.parse("2026-01-01")` — read as UTC

So a window with no offset is accepted, and the two forms above disagree with each other by the host's offset.

The event-write path already enforces this. `packages/calendar-service/src/build.ts:63` declares `OFFSET_BEARING` and `build.ts:98` tests against it. Only the read path skips the check.

## Reachability

`from` and `to` are declared as bare `string` in `typespec/main.tsp:431` and `:435`, so there is no `format: date-time` for ajv to enforce ahead of the handler. Any API caller reaches it directly.

`typespec/main.tsp:423-424` promises a 400 for this input, so the documented contract and the implementation disagree.

On a host whose `TZ` is not UTC the window shifts silently by the local offset, and events at its edges appear or vanish. The repo rule is that business dates are ISO 8601 with an explicit offset; this is the read that does not hold the line.

No test asserts the refusal.

## Fix

Apply `build.ts`'s `OFFSET_BEARING` check in `readWindow` and return the `InvalidWindow` refusal already described in the comment and the spec. Share the one regex rather than writing a second.
