A dead-code sweep over `main` found the repo close to clean: zero unreferenced files, zero unused dependencies, and 5 unused exports out of 5,628. Three things are certainly dead and can go.

## 1. The `settings` and `errors` i18n namespaces are empty in every locale

`packages/web-client/src/lib/i18n.ts:14` declares four namespaces:

```ts
ns: ["common", "mail", "settings", "errors"],
```

`settings` and `errors` are `{}` — 2 bytes — in all four locales:

```
packages/web-client/public/locales/{en,nl,de,fr}/settings.json   2 bytes each
packages/web-client/public/locales/{en,nl,de,fr}/errors.json     2 bytes each
```

Nothing reads either namespace. i18next fetches all eight files at startup on the strength of that `ns:` entry alone, so this is eight HTTP requests for eight empty objects.

Delete the eight files and drop `"settings"` and `"errors"` from `ns:`. Both halves must land together — removing the files while the namespace list still names them turns eight empty responses into eight 404s.

**Do not touch `{nl,de,fr}/common.json`.** They are also empty, but `common` is the `defaultNS` and is live (`__root.tsx:53` reads `accessibility.skipToContent`), so an absent file becomes a 404 rather than an empty object.

## 2. `anchorWarnings` is unreferenced

`packages/web-client/src/lib/config-import.ts:406-410`. A whole-tree grep for `anchorWarnings` returns only the declaration. `packages/web-client`'s `exports` map is narrow — `./shell`, `./config`, `./auth/*`, `./styles/*`, `./vite-preset` — so `src/lib` is internal and this is not public API.

`FOLDER_PENDING_CODE`, which it uses, stays: it is also read at `:387`.

## 3. `CalendarSearch` is unreferenced

`packages/web-client/src/lib/calendar-route.ts:197`, a `z.infer` alias over `calendarSearchSchema`. Referenced nowhere, including by TanStack Router's `validateSearch` typing. The schema itself stays.

## Scope

Roughly 15 lines and 8 files. No behaviour change — the proof is that the existing suites pass untouched.

Deliberately **not** in scope: the dead translation keys in `en/mail.json` and `en/common.json`. Those carry real strings and, in the case of the `sidebar` block, real translations. Removing them is a product decision about whether i18n is live or vestigial, not a cleanup. Recorded as an observation on the run ledger #1083 instead.
