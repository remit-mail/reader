The delete-exhaustion resolver writes `status: active` while leaving `mailboxId` pointing at Trash and `uid` holding the *source* folder's value. Every guard that protects against that mismatched pair keys off `status === moving`, so clearing it classes the row "consistent" — and the UI then offers "Delete permanently", which expunges Trash by a uid that names a different message.

## Where

`packages/imap-worker/src/handlers/message-delete-terminal.ts:103-106` writes `{ status: active, syncStatus: failed }` on BROKEN and touches neither `mailboxId` (already Trash, from `updateForMove`) nor `uid` (still the source's).

`packages/mailbox-service/src/placement-settled.ts:38-43` — `bindsForeignUid` returns false unless `isPlacementUnsettled`, i.e. `status === moving`. So `placementBindingOf` answers `"consistent"` and `MessageMoveService.settledPlacement` (`packages/mailbox-service/src/message-move.ts:942-943`) returns the row unexamined.

`message-move.ts:398-415` — `isInTrash` is true, so the row falls through to `permanentDeleteMessages`, and `packages/imap-worker/src/handlers/message-delete.ts:582` runs `connection.deleteMessages([uid])` against Trash with the source folder's uid.

## Reachability

Three transient failures (`DEFAULT_MESSAGE_DELETE_MAX_ATTEMPTS = 3`, `message-delete.ts:34`) on a delete whose message is still at the source reach `settleExhaustedDelete` and settle BROKEN.

The row then renders in Trash with `isDeleted: true`, and `packages/web-client/src/lib/format.ts:293-299` resolves a target whose `mailboxId` is the Trash mailbox to `"permanent"` — so the dialog reads "Delete permanently" (`format.ts:389`).

Nothing repairs the row in between. The `emitMoveResync` that follows cannot help, because `repointsOnSighting` also refuses `syncStatus: failed` (`message-sync.ts:159`, pinned by `message-sync-repoint.test.ts:313`).

## Distinct from what is already filed

#1005 is the `status: moving` variant, which `settledPlacement` correctly *refuses*. This is the inverse: settling to `active` is what switches that refusal off. #1002 is only about neither field reaching the wire.

## Not established

Not reproduced. Whether the expunge destroys a *different* message depends on Trash holding a message at that source uid. Without the collision the outcome is the weaker one — reader deletes its own rows for a message still sitting in the Inbox on the server.

**No fix is proposed here deliberately.** The settle needs to leave the pair readable as inconsistent, or repair it, rather than clearing the one flag every guard reads — but choosing between those is a design decision about what a BROKEN delete means, and it should not be pre-empted by a ticket written from reading alone.
