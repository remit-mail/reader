`handleMessageCopy` reads an absent COPYUID entry as evidence the copy failed. On a server without UIDPLUS the COPY succeeds and the row is left at `uid: 0`, `status: moving`, `syncStatus: failed`, permanently — no retry, no DLQ entry, no metric.

## Where

`packages/imap-worker/src/handlers/message-copy.ts:145-203`:

```ts
const newUid = result.uidMap.get(uid);
if (newUid) { … } else { … "Source message not found in COPYUID response - may have been deleted" … update({ syncStatus: failed }) }
```

`packages/imap-worker/src/imapflow-connection.ts:1131-1134` returns an empty map when imapflow answers `false`, so the branch conflates "the server has no UIDPLUS" with "the server matched nothing".

## This shape was already removed once

It is verbatim what #979 (closed) took out of `message-delete.ts`. That issue's own body lists the handlers that already probe by Message-ID before deciding — `message-move.ts:279-296`, `placement-move-push.ts:74-80`, `append-sent-message.ts:227`, `outbox-message.ts:13` — and concludes the delete path "is the only one that did not get it". `message-copy.ts` was not in that list and still has not been fixed.

## Reachability

`MessageBulkOperations_copyMessages` (`packages/backend/src/handlers/message.ts:971`) → `MessageMoveService.copyMessages` → `MESSAGE_COPY`. No race, no special state: every copy on such an account.

The row cannot be repaired afterwards. A later sync of the destination resolves the server's copy to the *source* messageId and is then declined by the `holdsCopyOf` guard (`message-sync.ts:1487`, `:1548-1556`).

## Not covered

`packages/imap-worker/src/handlers/message-copy.test.ts:166` pins the current behaviour — "marks the copy failed when the COPYUID response omits the source uid" — so the fix has to change that test.

## Not established

Not reproduced against a live non-UIDPLUS server. Dovecot, which the e2e stack runs, advertises UIDPLUS, so e2e cannot reach this path. The claim that such servers are real rests on this repository's own position in the four handlers listed above, which all probe rather than assume. That is the same caveat #979 carried and was accepted on.

## Fix

Probe the destination by Message-ID before reaching a verdict, the way `message-move.ts:287-296` does. `searchMailboxByMessageId` is already exported from that module.
